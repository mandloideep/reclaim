# Releasing reclaim

A release is a tag.
Pushing a tag such as `v0.1.0` runs `.github/workflows/release.yml`, which publishes the GitHub release and updates the Homebrew formula.
Nobody builds or uploads anything by hand.

## One time setup: the tap token

The release job pushes `Formula/reclaim.rb` to [mandloideep/homebrew-tap](https://github.com/mandloideep/homebrew-tap).
The workflow's own `GITHUB_TOKEN` can only write to this repository, so the job needs a second token, read from the repository secret `HOMEBREW_TAP_GITHUB_TOKEN`.
Without it the release job stops before it publishes anything.

1. Open GitHub, Settings, Developer settings, Personal access tokens, Fine-grained tokens, and choose Generate new token.
2. Resource owner: `mandloideep`.
3. Repository access: Only select repositories, and select `mandloideep/homebrew-tap` and nothing else.
4. Repository permissions: Contents, Read and write.
GitHub adds Metadata, Read-only, on its own.
No other permission is needed.
5. Pick an expiration and generate the token.
6. In `mandloideep/reclaim`, open Settings, Secrets and variables, Actions, and choose New repository secret.
Name it `HOMEBREW_TAP_GITHUB_TOKEN` and paste the token as its value.

When the token expires, generate a new one the same way and update the secret.
A classic token with the `public_repo` scope also works, but it can write to every public repository of the account, so the fine-grained token is preferred.

## Cutting a release

1. Make sure `main` is green in CI and holds everything the release should contain.
2. Tag the commit and push the tag:

```
git checkout main
git pull
git tag -a v0.1.0 -m "reclaim v0.1.0"
git push origin v0.1.0
```

3. Watch the `release` workflow in the Actions tab.

Tags follow semantic versioning with a leading `v`.
A tag with a suffix, such as `v0.2.0-rc.1`, is published as a prerelease and does not update the formula.

## What the workflow does

1. It runs the CI workflow, `.github/workflows/ci.yml`, with every job: build, vet and race tests on macOS and Linux, lint, and the Docker integration test.
Nothing is published unless they all pass.
2. It checks that the tag points at a commit on `main` and that `HOMEBREW_TAP_GITHUB_TOKEN` is set.
3. It runs GoReleaser, `go run github.com/goreleaser/goreleaser/v2@v2.18.2 release --clean`, with the newest stable Go.
The job has `contents: write` on this repository and no other permission.

GoReleaser reads `.goreleaser.yaml` and:

- builds `cmd/reclaim` for darwin and linux on arm64 and amd64, with CGO disabled, `-trimpath` and `-X main.version={{.Version}}`, so `reclaim version` prints the tag;
- packs each binary with `LICENSE` and `README.md` into `reclaim_<version>_<os>_<arch>.tar.gz` and writes `checksums.txt` with their SHA-256 sums;
- creates the GitHub release for the tag with notes generated from the commit subjects since the previous tag;
- writes `Formula/reclaim.rb` with the archive URLs and checksums and pushes it to the tap with the commit message `Update reclaim to <tag>`.

There is no `CHANGELOG.md`.
The release notes on the GitHub release are the change log.

## Release notes

The notes list commit subjects since the previous tag, oldest first, in three groups:

- New: subjects that start with `Phase N:`, `Add`, `Support`, `Scan`, `Show`, `Print` or `Render`.
- Fixes: subjects that start with `Fix`.
- Other changes: everything else.

Merge commits are left out, and so are commits that only change documentation.
GoReleaser can only judge a commit by its subject, so a documentation-only commit is recognized by how its subject starts: `Docs`, `Document`, `Rewrite the README`, `Update DESIGN.md` and the like, or `Add phase N worker brief`.
A subject that only mentions the README further on, such as the squash commit of a phase, stays in the notes.
Write subjects with that in mind, and edit the notes on the GitHub release afterwards if one slipped through.

## Verifying the formula

After the workflow finishes:

1. The release page lists four archives and `checksums.txt`.
2. The tap has a new commit, and `Formula/reclaim.rb` names the new version, four URLs under `releases/download/<tag>/` and four `sha256` lines that match `checksums.txt`.
3. On a Mac with Homebrew, install it and run the formula's test:

```
brew install mandloideep/tap/reclaim
reclaim version
brew test reclaim
```

`reclaim version` prints `reclaim v0.1.0` followed by the Go version and the platform.
The formula installs bash, zsh and fish completions generated by `reclaim completion`, so after opening a new shell `reclaim scan --tier <Tab>` offers `A`, `B` and `C`.

## Checking the configuration without releasing

GoReleaser runs through `go run`, so it is never installed and never enters `go.mod`:

```
go run github.com/goreleaser/goreleaser/v2@latest check
go run github.com/goreleaser/goreleaser/v2@latest release --snapshot --clean
```

`check` exits with status 2 and the message "configuration is valid, but uses deprecated properties", because GoReleaser deprecated the `brews` section in favor of Homebrew casks.
The formula is kept on purpose: it builds on Linux as well as macOS, runs a `test` block and installs shell completions.
Moving to `homebrew_casks` is a separate change for when GoReleaser drops `brews`.

The snapshot writes everything to `dist/`, which git ignores: the four binaries, the archives, `checksums.txt` and the formula in `dist/homebrew/Formula/reclaim.rb`.
It publishes nothing.

## Screenshots

The README screenshots in `docs/screenshots` come from a fixture machine, never from a real one.
Regenerate them after changing what `scan`, `here` or the checklist print:

```
scripts/screenshots.sh
```

CI runs the same test without the update switch and fails while the committed terminal output in `cmd/reclaim/testdata/screenshots` is out of date.
